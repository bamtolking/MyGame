## 2. 브라우저 실기동 (Playwright, 헤드리스 Chromium) — `npm run e2e`

뷰포트 360×800, 390×844, 430×932 (isMobile, hasTouch, DPR 2). `play/index.html`(단일 파일 빌드)을 열어 실제 탭 입력으로 진행. 결과: **3개 뷰포트 모두 페이지 오류·콘솔 오류 0, "E2E OK"**. 스크린샷 43장은 `e2e-out/`(git 제외)에 있으며 `npm run e2e`로 재생성된다.

실제로 수행·확인한 흐름(각 뷰포트 공통):

1. 제목 → "새로 시작" → 연습 시작. 손님 착석 → 구이 버튼 2회 탭 → 보드에 불씨 꼬치 2개 → 첫 음식 탭(선택 강조) → 둘째 음식 탭 → 치즈 꼬치 1개로 합성 확인.
2. 주문 카드 "준비 완료" 표시 확인 → 카드 탭 → 접수 → 직원이 실제로 이동해 전달: `serviceWait=2.23초`, 판매 18 + 팁 2 장부 기록. 연습 후 코인 0 확인(연습 수입 미정산).
3. 배치 화면: 좌석을 배식구 옆(1,0)으로 옮겨 경로 2칸→0칸 확인. 두 번째 좌석을 (0,1)에 놓으려 하면 "놓을 수 없어요: 배식구와 출입구 사이 통로가 막혔어요." 표시, 확정 버튼 없음. 좌석을 (4,2)로 옮겨 경로 5칸·편도 2.5초로 재계산 확인.
4. 1일차 영업: 음료 버튼 길게 누르기(950ms) → 6개 생성, 손을 뗀 뒤 0.6초 후에도 6개(연속 생성 정지).
5. 일시정지: 영업 시간이 5.33초에서 0.7초 동안 변하지 않음, 계속하기 후 다시 진행.
6. 봇이 1일차를 끝까지 진행(배속 6~8배, 화면은 실제 UI 갱신): 서빙 8명, 판매 116/82/100 + 팁, 정산 후 코인 반영, 2일차 해금, `settled=true`.
7. 결과 화면에서 새로고침 → 코인 변화 없음(중복 입금 없음).
8. (390 뷰포트) 영업일 선택 화면 → 4일차 준비: 좌석·장식 구매 후 코인 차감·가게에 배치 확인 → 4일차 영업 시작(달빛 미식회: 3~4단계 주문, 4좌석, 대기줄 표시) → 저장 → 새로고침 → "영업 이어하기" 버튼 → 일시정지 상태로 복원(t=66.5초, 보드 음식 14개, 4일차).

## 3. 수정한 오류 (개발 중 발견)

- 보드가 폭 기준 정사각형으로 잡혀 작은 화면에서 주문 카드·정보줄을 덮음 → 남은 높이에 맞춰 JS로 크기 계산(ResizeObserver).
- 화면 전환 후 이전 화면의 토스트가 남음 → 전환 시 제거.
- 외부(봇)에서 보드가 바뀌면 정보줄의 빈칸 수가 갱신되지 않음 → 매 프레임 보드 변경 감지 시 갱신.
- 밸런스: 초기값은 봇이 1.2초/조작으로도 전원 서빙해 좌석·배치 선택이 무의미 → 식사 시간 증가·인내 감소·도착 간격 단축 (BALANCE_REPORT 참고).
- 테스트 기대값 오타 1건(BFS 경로 길이 7 → 8).

## 5. 알려진 제한사항

- e2e 스크립트는 `window.__app.timeScale`로 시간을 배속하고 `window.__dbg`로 조작 함수를 직접 호출한다(디버그 노출). 실제 사용자 조작은 연습 영업·배치·길게 누르기·일시정지·카드 탭 부분만 실제 탭으로 검증했다.
- e2e 결과의 수입 값은 시드가 매번 무작위라 실행마다 다르다.
